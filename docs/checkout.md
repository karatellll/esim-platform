## Подтверждённый контракт

21 октября 2026 пользователь предоставил полный Swagger `D:\esim\doc.json`.
Нужные маршруты и связанные модели сохранены в
[provider-orders.swagger.json](contracts/provider-orders.swagger.json) с SHA-256 исходного файла.
Это проверка контракта и реализация по нему; реальный платёж и выпуск eSIM не проводились.
`localhost:8080` внутри Swagger не заменяет внешний `ESIM_PROVIDER_BASE_URL`.

| Наш маршрут | Поставщик | Назначение |
| --- | --- | --- |
| `POST /api/checkout/summary` | `POST /v1/sdk/orders/summary` | Персональный расчёт после входа; до входа только предварительная цена каталога |
| `POST /api/orders` | `POST /v1/sdk/orders` | Создание одного заказа и получение `payment.url` |
| `GET /api/orders/{id}` | `GET /v1/sdk/orders/{id}` | Проверка оплаты, выпуска и данных установки |
| `GET /api/orders?limit=50&cursor=…` | `GET /v1/sdk/orders` | Покупки текущего аккаунта с пагинацией |

SDK-запросы используют серверный ClientToken отдельного пользователя:
`external_user_id=tursim-user:<UUID аккаунта>`. Служебная идентичность каталога
не используется для покупок. PartnerToken, PublishableKey и ClientToken остаются на сервере.

Запрос расчёта поставщику: `{"ids":["<storefront_plan_id>"]}` — ровно один тариф.
Денежные поля, несмотря на суффикс `_minor`, описаны поставщиком как основные
денежные единицы: `45.5 RUB` показывается как `45,50 ₽`, без деления на 100.
Цена и валюта никогда не принимаются от клиента.

## Пользовательский сценарий

1. Покупка страны, региона или глобального пакета открывает оформление поверх тарифа.
2. Гость вводит почту, подтверждает код через существующий вход и возвращается
   в ту же форму. Сам вход не создаёт заказ. Покупки привязываются к аккаунту.
3. После входа сервер получает персональный расчёт и сохраняет котировку на 5 минут.
   Клиент получает `quote_id`, стоимость и параметры пакета.
4. «Оформить» передаёт только `{"quote_id":"<UUID>"}`. Сервер повторно проверяет
   стоимость и параметры. Изменение цены или истечение котировки требует нового
   расчёта и повторного нажатия после просмотра суммы.
5. Сервер сохраняет намерение, тело запроса и UUID `Idempotency-Key` до обращения
   к поставщику. При двойном нажатии, таймауте или перезапуске повтор использует
   прежний ключ и тело. При известном ID читается существующий заказ.
   Повторное открытие оформления с незавершённым заказом продолжает его.
6. Приложение открывает HTTPS `payment.url` кассы. Если автоматическое открытие
   заблокировано браузером, остаётся кнопка «Перейти к оплате» с фактической суммой.
   Если цена изменилась уже при создании, автоматического перехода нет:
   показывается новая сумма для явного подтверждения.
7. Состояние берётся только из `GET` заказа. Возврат из браузера не означает оплату.
   При `pending_payment` / `paid` / `provisioning` опрос идёт раз в 5 секунд только
   на открытом экране и в активном приложении. После возврата из кассы проверка возобновляется.
8. Поставщик сам обрабатывает webhook PSP и выдаёт eSIM после `captured`.
   Дополнительного `POST /v1/partner/esims` в этом сценарии нет.
9. При `delivered` и `payment.state=captured` показываются доступные QR/LPA,
   SM-DP+ и Matching ID. Частичная выдача повторно запрашивается; временный QR
   обновляется перед истечением. Отменённым/возвращённым заказам данные установки
   не выдаются нашим API. «Мои eSIM» показывает реальные покупки и остаток,
   если поставщик уже получил usage; `null` не превращается в выдуманный ноль.

Экран покупки и три вкладки установки переработаны по Figma `64:4122`,
`64:4177`, `91:4495`, `91:4816`: [installation.md](installation.md).
Кнопка «Установить eSIM» открывает шторку поверх купленной eSIM, «Позже»
ведёт в «Мои eSIM». QR скачивается через новый приватный `GET /api/orders/{id}/qr`;
после обновления сервера нужен перезапуск API.

HTTP 402 от создания не означает отсутствия заказа: `error.detail` содержит
`order_id`; сервер сохраняет его и читает состояние без повторного выпуска.
Неизвестные значения статуса eSIM допускаются и получают нейтральную подпись.

## Ограничения API и настройки кассы

В `summary` и `createOrderRequest` нет почты, промокода, страны карты или метода
оплаты. Почта подтверждается нашим входом. Промокод честно возвращает
`promo_unavailable`; скидки не имитируются. Переключатели способов оплаты
воспроизводят макет, но не передаются как неподтверждённые поля: доступный
способ окончательно выбирается в кассе, о чём есть подпись в форме.
Пользовательского API отмены и выдачи чеков в подключённых методах нет.

`ESIM_PAYMENT_RETURN_URL` необязателен. Допустим только абсолютный HTTPS URL,
до 512 символов, с не более чем одним `{order_id}`; префикс должен быть разрешён
оператором PSP. Без настройки поставщик возвращает на свои страницы результата;
пользователь возвращается в приложение для проверки заказа. Своего публичного
HTTPS возвратного маршрута в этом локальном приложении пока нет.

`ESIM_PAYMENT_ALLOWED_HOSTS` по умолчанию содержит `payform.aurapay.tech`,
домен из предоставленного контракта. Неизвестные домены, HTTP, ссылки с логином,
посторонним портом и истёкшие платёжные ссылки не передаются клиенту.
Если оператор изменит домен кассы, настройка меняется на сервере.

`ORDERS_DATABASE_PATH` по умолчанию — `apps/api/var/orders.sqlite3`.
SQLite создаётся автоматически для локального запуска. Сохраняйте базу заказов
и базу аккаунтов между перезапусками: в них привязка покупок и защита повторов.
Токены, платёжные URL, QR и коды активации в базу заказов не записываются.
Для нескольких серверов нужна общая надёжная база; текущий файл не является
готовым распределённым хранилищем. База и WAL исключены из Git.

## Проверки и запуск

`apps/api/tests/test_checkout.py` использует изолированные SQLite и
`httpx.MockTransport`: персональная идентичность, точное тело запросов,
повторы, таймаут после создания, перезапуск, параллельные нажатия, обновление
SDK-токена с сохранением ключа, чужой заказ, изменение/истечение цены, 402,
возврат, безопасность ссылок и частичная выдача. Реальных списаний в тестах нет.

Итог проверки 21 октября: 102 серверных теста, включая 19 проверок оформления,
и 26 тестов клиентской логики прошли. Web-экспорт собран успешно. Пользователь
установил `expo-secure-store`; повторная полная проверка TypeScript прошла.

Общие DTO: `packages/shared/contracts/checkout.ts`; OpenAPI и JSON Schema
обновляются через `apps/api/scripts/export_contracts.py`.

После обновления кода перезапустите API из обычного PowerShell:

```powershell
& D:\esim\restart-api.ps1
```

`D:\esim\apply-local-updates.ps1` пропускает повторную установку совместимого
SecureStore и проверяет TypeScript перед перезапуском. Серверный скрипт теперь
проверяет доступ к поставщику до остановки работающего API, распознаёт старый
запуск с относительным `--app-dir apps/api` только вместе с сигнатурой ТурСим,
учитывает Python-лаунчер и дочерний сервер. Чужие процессы не останавливаются.
Новый запуск использует абсолютный путь, отдельные логи в `D:\esim\.run` и
сверяет PID слушателя с новым логом и наличием маршрутов заказов: старый
ответ `/health` больше не считается успешным перезапуском.
Проверка скрипта: `scripts/test-api-restart.ps1` — 12 проверок распознавания
процессов и защиты от ложного успешного запуска. В изолированной среде внешняя
сеть запрещена; новый preflight оставляет действующий сервер работающим.
Native-сборка на устройстве ещё не проверялась. Веб использует отдельное
хранилище с HttpOnly cookie.
